# Direct-Surplus V1: design and validation plan

Goal: the StickS3 uses the phone hotspot to call Surplus directly, without a VPS. **Not implemented yet.** The existing `StickS3/` build still requires the bridge and must not be represented as the direct version. Keep it intact as a fallback until direct paths pass tests.

1. Provision a scoped Surplus buyer key on the device via the setup flow, not in source code. Store in NVS; document that physical access or unencrypted flash may expose it. Use HTTPS with the correct verified CA, a configurable model allowlist, and avoid secrets in logs and URLs. Budget limits must be enforced at the account/key where available; a local counter is only advisory.
2. Upload bounded 16 kHz WAV microphone audio as multipart to `/v1/audio/transcriptions`; account for content-length, timeouts and limited memory. The documented route is file transcription; do not promise Gemini Live interim results without a separately verified streaming API.
3. Classify the transcript as `image`, `song`, `speech`, or `clarify` with a user-configured Surplus `/v1/decisions` model; account for OpenAI vs JEV schema compatibility, access and no-seller errors, and calibrated thresholds validated on held-out data. On errors or low confidence, ask for clarification rather than silently start an expensive generation. Do not mistake a classifier's label for a response or image prompt.
4. Call chat as needed to draft/rewrite speech or media prompts; call native Surplus speech, image, and async music APIs. Support explicit provider output formats, bounded memory, partial/chunked HTTP responses, async polling, artifact authentication and redirects without forwarding credentials cross-origin. Preserve cancellation behavior and disclose that a submitted job may still be billed. No retry of ambiguous paid submissions without documented idempotency.
5. Decode media using bounded buffers, handle 135×240 color images and half-duplex StickS3 speaker audio, and release temporary buffers. Handle unsupported formats, oversized assets and network disconnects visibly. Compare peak PSRAM and stack use with Wi-Fi/TLS active. Compile with pinned dependencies and exercise simulated provider responses, then test transcription, all media modes, power, Wi-Fi, failures and billing on the actual stick.
6. Compare fixed rules, a normal generative router, and remote decision models using the same held-out synthetic tasks. Record intent accuracy, confusion matrix, confidence calibration, latency, refusals, task success and actual total cost (routing plus follow-on calls); do not infer a cost or quality win from model name or discount.

## Local inference

The StickS3 has 8 MB PSRAM and 8 MB flash shared with firmware, Wi-Fi, TLS, audio and image buffers. Tiny task-specific models such as ESP-SR WakeNet or fixed command classifiers may be practical after measuring real memory, CPU, false activations, battery and audio half-duplex interactions; they are not general transcription or a general-purpose LLM. Many open decision models are far too large for these limits. Existing V1 scope should prioritize direct calls and push-to-talk; local wake word is an experiment, not a promised capability. See https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/wake_word_engine/README.html.
